# Android capture retains only provable structured candidates

Superseded in part by ADR-0011 (2026-11-16): Android no longer has a notification listener, its parsers, CMB capture, or listener health alerts. The candidate, queue, privacy, confirmation and enrichment boundaries below still apply.

Amended by ADR-0014 (2026-11-20): while the user has item recognition switched on, scrubbed text of the order pages around a Taobao or Pinduoduo payment is uploaded with its candidate and sits in the encrypted queue until then. "Raw text is never saved, uploaded, or logged" holds unchanged with the switch off, and for logs and server storage either way.

Android grants notification access at app level, but the production listener accepts only user-enabled Alipay, WeChat, and CMB packages. Alipay v2 reads title, text, bigText, subText, summaryText, infoText, and tickerText in memory, normalizing whitespace and deduplicating fields. One distinct valid CNY amount is still required across all fields. Merchant extraction prioritizes explicit merchant/payee or bracketed context, then paid-to patterns, then paid-at/order-success patterns. Multiple merchants at the highest matching priority remain null; generic Alipay/payment-alert/quick-payment names are excluded. WeChat and CMB retain prior fields and rules: WeChat requires success markers; CMB accepts one transaction amount directly associated with debit, purchase, payment, expense, withdrawal, transfer-out, or bill-payment semantics. Balances are not transaction amounts. Chats, summaries, failures, refunds, income, and incomplete notifications are discarded in callback memory. Raw text is never saved, uploaded, or logged. Devices retain only AES-GCM encrypted structured candidates; the server retains canonical fields and a SHA-256 digest covering participating fields.

Candidates are not posted transactions. The server accepts explicitly registered Alipay v1/v2, WeChat v1, and CMB v1 parser identities. Unknown `parserId + parserVersion` pairs are rejected individually without blocking other events. After validation, categorization, and deduplication, candidates await explicit confirmation unless the user has explicitly enabled automatic posting for that platform and the amount is within the configured cap. Only unique candidates can follow this automatic path; possible and exact duplicates still require review. Duplicates then link existing transactions; overrides bind the current assessment digest. Only Ledger Transaction posts, retaining `notification_capture` provenance. Strict omission is preferred to guessed fields; automatic posting remains bounded by explicit platform authorization and duplicate checks. Payment-app changes may temporarily cause missed captures until parsers are updated from anonymized device samples.

After upload, Android may publish grouped candidate notifications for all three sources. If a merchant is missing, sending a name through system `RemoteInput` explicitly confirms posting; otherwise one-tap confirmation is available. Notifications are private, with lock-screen public versions excluding amount, merchant, and source. Input enters an Android Keystore encrypted action queue bound to the captured user. WorkManager arguments, logs, and notification extras never hold plaintext. Dismissing a notification removes only the reminder, not the server candidate. Without notification permission, the app's Add merchant action uses the same endpoint. The server atomically updates merchant, reclassifies, deduplicates, and posts. Network failures are retryable; switching accounts must never submit an old user's actions as the new user.

Alipay statements may enrich a unique pending candidate or its posted transaction for the same user, amount, currency, and a time difference within five minutes. Amount, currency, and time remain notification facts. Generic system values may adopt statement values directly; user-content conflicts require per-field decisions. Pending candidates retain `notification_capture` provenance; existing transactions append amendments without rewriting origin. Alipay transaction IDs become append-only supplemental evidence. New transactions, amendments, candidate completion, evidence, and import results commit together. Changed target revisions or multiple matches stop automatic enrichment.

Listener disconnection records a generic health error, requests Android rebinding, and schedules a WorkManager check after 30 seconds. Boot schedules the same check only when capture is enabled. Revoked access or persistent disconnection can trigger fixed health alerts without financial or account information, at most once per issue every 12 hours. Reconnection cancels alerts and resets cooldown. Without ordinary notification permission, errors appear only in app settings. Recovery uses no accessibility service, persistent foreground service, overlay, or local plaintext ledger storage.

Devices may retain local counts by source + parserId/version + acceptance/rejection reason, including accepted-without-merchant counts, for current and previous parser versions only. Counts contain no text, amount, merchant, summary, or evidence hash, are never uploaded/exported, and can be reset. Server field origins must explicitly be `parser`, `system_default`, `categorization_rule`, `quick_input`, `manual_edit`, or `bill_enrichment`. Unprovable historical origins migrate to `legacy_unknown`; nonempty fields must never be assumed to be user input.

Deduplication algorithm v2 treats CMB debits and Alipay/WeChat payments with equal amount and currency within five minutes as possible duplicates even if merchant labels differ or are absent. Amount and time alone never authorize automatic merging. The shared review inbox paginates notifications, includes all pending screenshot jobs, and shows recently completed captures with transaction links. Batch confirmation accepts at most 20 reviewed unique candidates with explicit confirmation versions, rechecks current facts in one transaction, and rolls back the entire batch if any item changes or needs review.
