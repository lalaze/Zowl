# 采集日志保存在本机

状态：已实现，待真机验证。日期：2026-11-17。

## 背景

漏记一笔付款时，要知道那一刻看到了哪些窗口、为什么没有生成候选。ADR-0012 的 `CaptureTrace` 只写 logcat，而且要先用 adb 打开；测试用的手机（Android 16）logcat 的 main 缓冲区默认只能保留约 6 分钟，等用户发现漏记，现场早已被冲掉。服务是否被划卡清理、冻结后多久重启，也只能碰运气从 events 缓冲区查到。adb 调大缓冲区重启后就失效（`persist.logd.size` 不允许 shell 设置）。

用户的要求：遇到不支持的付款，反馈后马上能按日志调整规则。

## 决定

- `CaptureTrace` 的每条消息都写入本机日志 `CaptureLog`，不再需要 setprop。输出到 logcat 仍需 `adb shell setprop log.tag.ZowlCapture DEBUG`。
- 位置：应用的外部私有目录 `/sdcard/Android/data/com.zowl.mobile/files/capture-log/`，读不到时退回内部存储。每个本地日期一个文件（`2026-11-17.log`，写满 2 MiB 后续写 `2026-11-17.2.log`）；~~保留 7 天，总量上限 16 MiB，超出先删最旧的~~（已由文末 `2026-11-22 改为永久保留` 取代）。真机上已确认 adb shell 可以直接读这个目录；其他应用没有权限。卸载应用时一并删除。
- 记录范围仍是结构信息，和 ADR-0012 的跟踪一样：窗口类名、文字行数、金额个数、是否有成功标题、拒绝原因代码。新增的内容如下：
  - 每行的时间；
  - 进程启动：pid、版本、系统版本、机型、时区；
  - 上一个进程怎么结束的：系统 `ApplicationExitInfo` 的原因、重要性和系统描述（例如 HyperOS 的 `SwipeUpClean`）；
  - 无障碍服务的连接、解绑和销毁；
  - 每个平台在"采集关闭／来源关闭／未登录／就绪"之间的切换；
  - 每次接受或拒绝（平台、解析器、原因代码，以及是否带商户）；
  - 上传结果（HTTP 状态，以及每条的 status、reviewStatus、code 和 resultCode）。
  
  前台窗口不属于事件所在的应用时，会记下前台应用的包名。不记页面文字、OCR 全文、金额、商户、账号、token 或图像。
- 连续重复的同一条消息只写一次，后面附一行重复次数。
- 写入在单独的线程上进行，失败直接忽略，不影响采集，也不参与放行决策。
- 导出：采集设置里"本地解析诊断"面板新增"导出日志"按钮。点击后把全部日志合并成一个文本文件，经 FileProvider（只开放这一个导出目录）交给系统分享面板。只在用户点击时发生，不会上传到服务器。

## 与既有决定的关系

- 取代 ADR-0012"`CaptureTrace` 只有通过 setprop 才输出"那一条。
- 与 ADR-0010"窗口类名只在内存保存"相冲突：用于放行决策的类名表仍只在内存里，但日志现在会把每次看到的类名连同时间写到磁盘。本地诊断里本来就保存了最多 16 个类名（ADR-0012），这次改动扩大的是条数和时间信息。
- ADR-0009 的本地 OCR 诊断（固定枚举、不保存逐次记录、没有分享接口）保持不变，那是另一份东西。这里的逐条、可导出的日志，是用户为排查漏记明确要求的例外；它仍守 ADR-0006/0010 的边界：原文和图像不落盘。

## 代价与已知风险

- 日志虽然没有金额，但记下了用户在什么时间打开了哪个支付应用的哪个页面、付款有没有被采集，这是行为记录。它只留在本机（原为 7 天后自动删除，2026-11-22 起永久保留，见文末）；导出的副本发给谁由用户决定。
- 在微信、支付宝里浏览时，每次页面静止都会写一行（重复的已合并）。估计每小时最多几百 KB（原由 16 MiB 上限兜底，2026-11-22 起改为旧文件压缩、剩余空间不足 500 MiB 时暂停写入）。
- 进程被冻结时什么都不执行，所以日志里没有冻结的那一刻，只能从时间空档和下次启动时记下的退出原因推断。
- 日志线程里还没写盘的几行，会随进程被杀一起丢失；末尾"重复 N 次"的汇总行同样如此。

## 验证

JVM 测试覆盖按日分文件、写满续写、重复合并、换行不能伪造新行，以及导出顺序（2026-11-22 起改测永久保留、压缩、低空间暂停和 zip 导出）；Flutter 测试覆盖导出按钮和"还没有采集日志"的提示。真机待验证：adb 读取、退出原因、系统分享面板。

## 2026-11-22 改为永久保留

实际使用中，漏记排查是定期集中回顾，而不是发现当天立刻处理；原先 7 天自动过期与 16 MiB 总量上限会让较早的漏记现场在回顾前已被删掉。因此调整保留、压缩、空间保护与导出方式，取代前文中"保留 7 天、总量上限 16 MiB、导出拼接单个文本文件"的决定：

- **不再自动删除**：取消 7 天过期和 16 MiB 总量删除，应用不再主动删除任何采集日志文件；日志仅在卸载应用或清除应用数据时随目录一并清除。
- **旧文件就地 gzip 压缩**：在日志线程打开新文件时（跨日、写满 2 MiB 切分片，或进程重启后首次写入），把所有已写完的 `.log`（早于当前写入日期，或已达到单文件上限且不是当前正在写的文件）压缩为同名 `.log.gz`。先写入 `<原名>.gz.tmp`，关闭后原子改名为 `<原名>.gz`，最后删除原 `.log`；残留 `.gz.tmp` 会被清理并重压，若 `.log` 与 `.log.gz` 同时存在则只删 `.log`（不覆盖已有 `.gz`），任何 IO 失败都保留原 `.log`。`openFile` 也会跳过已有 `.log.gz` 的分片名，避免冲突。
- **按文件名排序**：保留文件列表与导出顺序改为按文件名解析出的日期与分片号排序，不再依赖 `lastModified`（压缩会改变 mtime）；不符合命名模式的文件忽略。
- **低空间暂停写入**：写入前最多每 60 秒检查一次日志目录所在卷的可用空间。低于 500 MiB 时停止写入（不删除历史日志），只在暂停时记录一行 `log paused: low storage`；可用空间回到阈值及以上后记录 `log resumed` 并恢复写入。
- **导出为单个 zip**：`CaptureLog.export` / `CaptureLogFiles.exportTo` 改为生成 `zowl-capture-log-<yyyy-MM-dd>.zip`，按日期与分片顺序原样打包所有保留的 `.log` 与 `.log.gz`（分享 Intent MIME 类型改为 `application/zip`）。
- **Mac 端拉取、扫描与排查规程**：新增 `scripts/capture-logs.ts`（`pull` / `scan` / `mark-reviewed`）用于将本机日志同步到 Mac 并扫描疑似漏记流程；完整排查与修复步骤见 `docs/agents/capture-log-investigation.md`。
- **代价**：日志里“何时打开过哪个支付应用的哪个页面”的行为记录现在会一直保留在本机，直到卸载应用或清除应用数据才删除；内容边界不变——仍不记录页面原文、金额、商户或任何屏幕文字，也不会上传到服务器。
