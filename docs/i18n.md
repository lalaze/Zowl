# Chinese / English UI

Both clients show every screen in Chinese or English. The choice is per device:
the mobile app keeps it in SharedPreferences (`zowl-language`), the web app in
the `zemoney-locale` cookie. With no choice saved, mobile follows the phone's
language and web follows the browser's `Accept-Language`.

Copy is written inline as English/Chinese pairs, so a string can never be
missing its translation and the call site shows both:

| Where | How |
| --- | --- |
| Flutter, anywhere | `tr('Save', '保存')` from `lib/core/l10n.dart` (global; the app rebuilds every element on a switch) |
| Flutter dates/numbers | `DateFormat(pattern, intlLocale)` |
| Web client component | `const t = useT()` from `@/components/i18n/i18n-provider`; `useLocale()` for the locale |
| Web server component / page | `const t = await getT()` / `await getLocale()` from `@/lib/i18n/server` |
| Web metadata | `export async function generateMetadata() { const t = await getT(); ... }` |
| Web helpers outside React | take a `locale: Locale` (or `t: Translate`) parameter |
| Web dates/numbers | `Intl.*(localeTag(locale), …)` |
| Rich text with inline elements | `locale === "zh" ? <>…</> : <>…</>` |

Services, schemas and route handlers keep producing English messages.
`errorResponse` translates them for the requester through
`src/lib/i18n/server-messages.ts`; add the Chinese for any new message there
(a test fails when a literal error message has no entry). Server-written text
inside successful payloads (row issues, warnings, provider disclosures) is
translated by `localizedDataResponse` in API routes, `localizeServerData` /
`localizeServerMessage(message, locale)` when a page renders it directly.

Never translate user data (category names, merchants, notes), identifiers,
keys or log output. Tests run in English, so English copy is what they assert.

## Text the server writes into data

It is written once, in the language of the request that caused it, and stored
as-is (switching language later does not rewrite it). Route handlers pass
`await getLocale()` to the service as an explicit `locale` argument; services
never read headers, and callers without a request get English.

- **AI text**: categorization `reason` and screenshot-recognition `warnings`
  are requested from the model in the requester's language. Model text is not
  in the dictionary, so `localizeServerData` passes it through while fixed
  server warnings in the same list are still translated.
- **Payment captures**: generated descriptions and payment methods
  (`支付宝支付通知`, `招商银行扣费通知`, `微信支付成功页（本地识别）`; `支付宝` /
  `微信` / `招商银行`) follow the uploading device's `Accept-Language`. Nothing
  compares them by value, so English and Chinese rows mix safely.
- **Built-in categories** are named in the language of the request that
  created the account (setup, admin "add member"). Code finds them by key
  (`getDefaultCategory(db, userId, "other")`, `builtInKey` from
  `categoryManagementService.list`), never by name. When built-ins still carry
  the other language's default name, the Categories page offers to rename them
  (`POST /api/categories/built-in-names`), skipping names already taken.

Statement-imported values, model-extracted merchants and descriptions, and
everything typed by people stay exactly as they came in.

## Native text

**Android** strings live in `res/values/strings.xml` (English) and
`res/values-zh/strings.xml`. They follow the in-app choice, not the phone:
Flutter sends it over the `com.zowl.mobile/language` channel at start and on
every change (`lib/core/native_language.dart`), and `NativeLanguage.kt` keeps
it so workers, the notification listener and the accessibility service use it
while Flutter isn't running.

- Look up every native string through `NativeLanguage.localized(context)`.
- Native requests send `NativeLanguage.acceptLanguage(context)`.
- Errors kept for the app's capture settings are stored as a `CaptureError`
  key plus arguments and worded when read, so they follow a later switch.
- Notification channels are re-created with the new names on a switch.
- Manifest labels (the accessibility service and notification access lists in
  system Settings) are drawn by Settings in the phone's language, and
  notifications already on screen keep the language they were posted in.

**iOS** shows only the photo-library permission prompt natively. It lives in
`Runner/en.lproj` and `Runner/zh-Hans.lproj/InfoPlist.strings` (keep the
English in sync with `Info.plist`), and iOS picks it by the phone's or the
app's language in system Settings.
